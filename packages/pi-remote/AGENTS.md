# pi-remote Packaging

- Keep the source revision and `npmDepsHash` in sync with the committed root lockfile. Pi remains a host-provided peer; use `--legacy-peer-deps` so npm never installs a second SDK.
- Build all workspaces, then install only the CLI's production dependency graph. The extension needs `extensions/`, the runtime/server/protocol sources, and `packages/web/dist` at their original relative paths; the hub and browser build tools are not runtime dependencies.
- The Pi module lists `${pi-remote}/lib/pi-remote` as a local package so the extension and command always use the same revision, and renders `~/.pi/agent/pi-remote.json` from the `pi_remote_endpoint` sops secret. Only the hub address is templated: enrolment is a machine key, written as mutable state beside it (`pi-remote.machine.json`, `pi-remote.hub.json`) by `pi-remote pair` or `/pair` inside Pi, so a config rebuild never re-pins a hub. Revoking a machine is a hub-side action from the workspace's Pair dialog. It requires the `SESSION_BRIDGE_API_VERSION = 1` patch in `../pi-coding-agent`; extension and wrapper instance modes attach to stock Pi's interactive runtime without creating another session.
- Bumping `rev` needs both hashes: `nix run nixpkgs#nix-prefetch-git -- --url <repo> --rev <rev>` for `hash`, and `nix run nixpkgs#prefetch-npm-deps -- package-lock.json` for `npmDepsHash`. The lockfile changes with dependency edits, so a version bump that looks source-only can still need both.
- Verify a real extension load, `/reload`, and `/new`; TypeScript does not catch loader identity or session-ownership failures. Run `packages/runtime/test/extension-smoke.mjs` with `PI_REMOTE_TEST_PI` set to the installed SDK's `packages/coding-agent`, `PI_REMOTE_TEST_PI_LAYOUT=dist`, and `PI_REMOTE_TEST_PACKAGE=<output>/lib/pi-remote`.
